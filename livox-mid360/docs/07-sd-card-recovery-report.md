## 原始故障及已经确认的现象

树莓派异常断电后进入initramfs，自动文件系统检查退出4，报错：

```text
Superblock needs_recovery flag is clear, but journal has data.
UNEXPECTED INCONSISTENCY; RUN fsck MANUALLY.
```

在树莓派及Ubuntu虚拟机中运行交互式e2fsck后，均在日志恢复阶段出现：

```text
Run journal anyway<y>? yes
e2fsck: unable to set superblock flags on writable
WARNING: Filesystem still has errors
```

核对e2fsprogs 1.46.5源码后，这条错误对应日志恢复后又进入恢复分支的保护性退出，不是直接的写入系统调用错误，不能只凭它判定SD卡损坏。

已观察到的具体证据：

- 内核报告根分区块组127的块位图校验和错误，随后中止journal，并将ext4重新挂载为只读。
- 块设备`RO=0`表示未设置设备只读标志，与ext4因错误主动只读挂载是不同层面的状态。
- 记录中的`I/O error, dev fd0`属于虚拟软驱，不能作为SD卡I/O错误证据。
- `dumpe2fs`显示`needs_recovery`，journal sequence为`0x0000890f`，journal start为`11129`。
- 单独出现`Filesystem state: clean`不能证明全盘一致；`0 bad blocks`也不能证明经过了完整坏块扫描。
- 更换USB接口并重新插拔同一读卡器后，原卡修复仍在相同位置失败。用户暂无其他读卡器。

## 已完成的文件保全和副本测试

1. 在分区卸载后执行只读`e2fsck -f -n -v`，确认有位图、计数和校验和不一致。
2. 以`ro,noload`挂载根分区，避免读取文件时回放日志。
3. 将`/home`和`/etc`备份到虚拟机：

   `/home/<虚拟机用户>/pi-home-etc-before-fsck-20261110-002750.tar.gz`

   文件约71MiB，tar退出0，gzip完整性检查退出0。该文件不是整卡备份。
4. 提取包含内部journal的稀疏元数据镜像，保留原始副本，另复制一份做修复测试。
5. 测试元数据副本经过交互式e2fsck修复后，五个检查阶段均通过，只读完整复查退出0。该副本不含普通文件的完整内容，不用于回写SD卡。

这些结果表明副本中的文件系统结构有可修复路径，尚不证明原卡能够可靠保存写入。

## 建立安全的完整备份目标

虚拟机系统盘只剩约12GiB，不能保存约29.1GiB的原始整卡镜像，因此使用Windows C盘的共享目录。

VMware最初没有发布共享文件夹，已为当前虚拟机启用`pi-sd-recovery`，并保存启用前的VMX配置。Windows路径规范为`<Windows用户目录>\pi-sd-recovery`。

曾出现HGFS目录枚举EIO：Python从共享目录启动时，导入标准库前扫描脚本目录而失败。修正共享配置、重新挂载，并使用`python3 -I -S`隔离导入路径。之后对共享目录进行了真实的目录枚举、文件创建、同步、改名和重读测试。

虚拟机写入的16MiB测试文件与Windows独立读取的SHA256一致：

```text
45eed2df0666155e8e5d6d404084c391f0a49fa08eb82974d2f5db64a5203714
```

确认挂载类型为HGFS、目录身份正确、剩余空间约271GiB后，才允许开始整卡备份。

整卡备份在2026-11-10 01:35:08开始，04:27:25完成，耗时约2小时52分钟。期间读速波动较大，但最终没有读取错误或未救援区域。

- 原始镜像精确长度为`31266439168`字节。
- ddrescue map连续覆盖`0 .. 31266439168`，所有区域均为`+`。
- Windows的`Get-FileHash`与虚拟机的`sha256sum`分别完整读取同一镜像，SHA256完全一致：

### 2. 包含普通文件数据的完整根分区副本已修复

从整卡镜像提取根分区到`rootfs-work.img`，大小为`30728502784`字节。复制时计算输入区段SHA256，关闭并同步输出后完整重读输出，二者一致：

`495e723c6330b7e5cc766d46146095d3e3af05c545fe7b899e1d1380689ae594`

这是**修复前提取校验值**，修复完成后文件内容会变化，不能拿它核对修复后的镜像。

`repair-copy01`对该完整副本运行交互式e2fsck，日志恢复成功，修正块位图与空闲计数。退出1表示发现并修正错误。

`check-copy01`随后执行`e2fsck -f -n -v`，五个检查阶段全部通过，退出0。`dump-copy01`进一步确认：

- `needs_recovery`已清除。
- `Journal start: 0`。
- `Journal sequence: 0x0000895e`。

这是完整根分区副本，包含普通文件数据；与之前只含元数据的测试镜像不同。文件系统结构通过检查不代表损坏的ROS、Python、dpkg或二进制文件内容自动被修复。

修复后的完整根分区镜像SHA256：

`af04518a5172041a7383da1737ea37f19b100ec076f2899fb2115a5202fc69ff`

完整关闭写入句柄后重读整个输出，确认根分区与修复后的根副本SHA256一致，根分区前后所有字节与原始整卡镜像相应区域SHA256一致。最终大小为`31266439168`字节，SHA256：

### 3. 原卡未通过修复和复查

重新核对原卡仍为USB的`/dev/sdb`、两个分区均未挂载、RO=0，并与完整备份几何信息匹配后，进行了一次受控交互式原卡修复`repair-card01`。

```text

e2fsck: unable to set superblock flags on writable

```

退出码为12，即仍有未修复错误和操作错误。随后只读`check-card01`退出4，确认原卡仍有文件系统不一致。

### 4. 引导分区和结束状态

`check-boot01`对`/dev/sdb1`执行只读`fsck.fat -n -v`，发现dirty bit，退出1，工具明确输出`Leaving filesystem unchanged`。没有对它进行写入修复。已生成的恢复候选镜像原样保留该引导分区，并不宣称FAT已修复。

原卡于04:37通过`udisksctl power-off`安全弹出，退出0。临时root维修控制会话随后停止，最终状态为`stopped`。未格式化、重分区或把元数据镜像写回原卡；没有创建免密sudo或新的SSH服务。

此前为避免SD卡被桌面自动挂载，曾临时关闭GNOME自动挂载。原设置保存在虚拟机`/home/<虚拟机用户>/pi-sd-diagnostic-*/automount-before.txt`，本次控制通道不支持恢复该桌面设置，因此未声称已恢复。自动挂载关闭不妨碍通过“文件”手动挂载其他磁盘。

## 恢复选择及后续验收

以下是成功验收应满足的条件，不是声称原卡已经完成全部检查。本次仅前两项通过；原卡在第三项写入修复中失败，未进行成功修复后的重连或树莓派启动验收。

1. 整卡备份完整，保留原始镜像和map。
2. 从整卡镜像提取包含完整文件数据的独立根分区工作副本，修复并完整只读复查退出0。
3. 记录原卡主超级块和journal超级块的字节摘要及状态，再进行一次受控交互修复。
4. 比较修复后的实际字段，确认预期更新是否保留；重新连接后再次核对身份和离线检查。
5. 只有原卡完整检查退出0、重新连接复查仍通过，才报告原卡文件系统结构修复通过。
6. 文件系统修复不保证此前损坏的软件文件内容恢复正确；树莓派是否能启动还需实机验收。

若修复更新始终不能保留，应如实记录证据并保留数据，不把工具在副本上的成功当作原卡已修好。

目前符合该失败情形，不建议继续重复相同e2fsck命令，也不应无依据改变journal特性、切换备用超级块或写回元数据镜像。

可选恢复方法：

1. 保留原卡和完整原始镜像。优先准备一张健康的新SD卡，实际字节容量至少`31266439168`；不同标称32GB的卡实际容量可能略小，因此64GB更方便。
2. 可使用修复后的完整根分区副本提取项目、脚本和配置；之前的`/home`、`/etc`压缩备份也保留在虚拟机。复制恢复到新系统时，应选择性恢复用户项目和配置，不能把旧`/etc`整体覆盖新系统。
3. 若使用全盘恢复候选镜像写入新卡，应在工具中明确核对目标可移动卡的容量与型号，拔掉不相关移动磁盘；镜像写入会覆盖所选目标，不能选择Windows硬盘或虚拟机系统盘。本记录不提供原始磁盘覆盖命令。
4. 也可通过Raspberry Pi Imager在健康新卡上重装适配树莓派5的系统，再恢复项目。若继续使用ROS2 Humble，先确认所选Ubuntu镜像对树莓派5及Ubuntu22.04/arm64的支持情况；Raspberry Pi OS同样可用，但ROS安装方案与现有Ubuntu不同。
5. 新卡离线完整文件系统检查通过、冷启动成功、可以正常关机并再次启动，才进入ROS与雷达功能验收。现有ROS/Python/dpkg历史损坏需要单独重装或校验，不能用fsck结果替代。

未来避免再次损坏：执行`sudo poweroff`并等系统停止活动后再拔电；树莓派5使用质量可靠的5V/5A USB-C电源并满足外设功耗；避免雷达供电波动影响树莓派；采用正规渠道A2或高耐久SD卡，重要项目及时提交Git、定期离机备份。若长期写点云/rosbag，优先使用可靠SSD并监控空间、温度与供电。
