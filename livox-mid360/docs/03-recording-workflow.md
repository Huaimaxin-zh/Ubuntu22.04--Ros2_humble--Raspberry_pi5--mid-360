# 如何持续记录配置和问题解决过程

## 1. 每个问题记录一份 Markdown

建议按日期和主题命名，例如：

```text
docs/2026-11-09-eth0-address-after-reboot.md
docs/2026-11-09-ros-python-null-bytes.md
docs/2026-11-10-fastlio-build.md
```

从 [故障记录模板](../templates/problem-record.md) 复制一份，记录环境、原始错误、判断依据、修改、验证和剩余问题。不要只写“改好了”，应留下别人能够判断是否真的解决的证据。

例如此次网口问题：

- 现象：启动脚本提示缺少 `192.168.123.4/24`。
- 证据：`ip -br -4 addr show eth0` 没有对应地址。
- 处理：恢复临时地址；不改 Wi-Fi 默认路由。
- 进一步发现：`carrier=0`，还需要恢复物理链路。
- 验证：`carrier=1`、ping 成功、真实点云约 10 Hz 和 IMU 约 200 Hz。
- 限制：临时地址重启后可能再次丢失。

## 2. 代码与说明一起提交

你写的新脚本放 `user-scripts/`，在代码里解释关键操作，并在同一次提交中更新相应文档。例如修改网口检查提示时，同时更新故障说明和使用方法。

建议提交消息使用这些简单前缀：

| 前缀 | 例子 |
| --- | --- |
| `docs:` | `docs: 记录SDK初始化成功但网口无链路的排查过程` |
| `fix:` | `fix: 退出时唤醒点云和IMU等待线程` |
| `feat:` | `feat: 添加原生点云和IMU检查器` |
| `chore:` | `chore: 忽略构建产物和点云数据` |

一次提交尽量对应一个明确修改。这样以后使用 `git log`、`git show 提交号` 或 GitHub 网页就能找到问题和解决方法。

## 3. 把你自己的文件放进来

在 Remote-SSH 的树莓派终端，先找到真正的脚本：

```bash
# 先列出源码工作区中的脚本，只查看，不修改。
find ~/ws_livox/src -maxdepth 4 -type f \( -name '*.sh' -o -name '*.py' \)
```

找到确实由你编写的文件后，只复制需要记录的文件：

```bash
# 这里的 my_script.sh 是示例，替换为真实文件。
cp ~/你的目录/my_script.sh ~/projects/mid360-notes/livox-mid360/user-scripts/
```

不要把整个 `ws_livox` 或 `livox_runtime` 拖进仓库。第三方驱动修改应记录上游 URL、commit 和补丁；若需要长期开发驱动本身，建议在自己的驱动 fork 中管理完整源码，再由资料仓库链接过去。

## 4. 保留可以复查的证据

像 `evidence/2026-11-09-stream-result.json` 这样的小型结果文件适合提交。日志只保留解释问题需要的片段，并写清命令、测试时长和运行机器。

建议区分以下几个层次：

1. 能 ping：网络连通。
2. SDK 初始化成功：软件初始化完成。
3. 收到非空点云和 IMU：真实数据采集开始。
4. 频率和内容检查通过：当前测试窗口内接收正常。
5. FAST-LIO 出地图：算法链路另行验证。

不要把前一级的成功写成后一级已经完成。涉及路由器组播、Wi-Fi 或 SD 卡故障时，应区分“看到的现象”“支持的判断”“尚未验证的推测”。

## 5. 区分保存、提交、推送、部署

| 操作 | 结果 |
| --- | --- |
| VS Code 保存文件 | 改动写到当前电脑或远程树莓派磁盘 |
| `git add` | 选择本次提交要包含的内容 |
| `git commit` | 本机 Git 历史新增一个版本 |
| `git push` | 将提交同步到 GitHub |
| 复制脚本 / 编译 / 重启程序 | 更新实际运行环境 |

以当前 `runtime/env.sh` 为例：在 Git 仓库改它并推送，不会自动改变 `/home/xin/livox_runtime/env.sh`。确认修改无误后，还需要备份并部署到运行目录，再重新启动相关终端或驱动。

## 6. 推荐日常工作方式

日常以 Remote-SSH 打开的树莓派仓库作为主要工作目录。开始修改前 `git status`；修改后看 `git diff`，测试后记录结果，最后提交并推送。电脑本地副本需要查看最新内容时再拉取，减少两边同时改同一文件造成的冲突。

临时工作建议建立新分支，例如 `git switch -c docs/fastlio-install`；完成后推送该分支，用 GitHub Pull Request 检查和合并。
